# Clipboard command transport contract

## Status

Frozen for first-release browser-assisted model command transport.

## Purpose

This contract defines the explicit clipboard bridge used when a person moves one
backend-generated model request to an external LLM and returns its response to
Atrament. It keeps clipboard text as transport rather than document authority,
command parser, autosave mechanism, or substitute for MCP.

## Scope

The contract covers outbound Copy, inbound Paste, exact text transport, prompt
and context identity, untrusted model responses, browser responsibility,
clipboard lifetime, privacy, failure behavior, and parity with native MCP
command
workflows.

It does not define operating-system clipboard capacity, external model privacy
policy, final semantic command wire fields, browser permission UI, rich
clipboard
formats, or automated access to third-party chat applications.

## Contract

### Explicit outbound copy

The browser writes command-mode prompt text to the system clipboard only after
an explicit user Copy action. Copy is presentation transport; it does not mutate
the accepted notebook, create a semantic command, add history, or authorize a
later response.

The copied text is generated by the backend command-context capability. It
contains the admitted instructions, protocol description, base revision,
readable data, writable scope, constraints, capability information, and prompt
or context identity required by that model workflow.

The browser does not independently assemble semantic context or insert hidden
command authority into the copied text.

### Exact text preservation

The browser transports the backend-presented prompt as text. It does not parse,
normalize, reorder, truncate, reserialize, sanitize into another command format,
or execute command-like content before writing it to the clipboard.

Unicode, mathematics, JSON-like text, markup-looking text, and hostile-looking
source prose remain literal text. Exact transport does not mean the content is
trusted semantic input.

Backend-owned protocol and context limits determine whether a prompt or response
is admissible. Browser textarea capacity or one successful clipboard probe does
not define application protocol limits.

### Prompt identity

The presented request retains its backend-owned prompt or command-context
identity. Copying the same unchanged backend request does not create a new model
intent merely because the user clicked Copy twice.

Prompt identity is correlation metadata, not authentication. Possessing copied
prompt text or its identity does not grant access to session-private application
capabilities.

### Intentional data egress

Copy is an intentional boundary crossing. Notebook, task, source, citation, or
other readable context included by the backend leaves Atrament process memory
when the browser writes it to the operating-system clipboard and may then be
pasted into an external application.

The backend therefore includes only the semantic data admitted for that model
request. Browser session secrets, MCP admission material, hidden temporary
paths, internal repository paths, and unrelated retry identities are not copied
as command context.

Atrament documentation and UI must not claim copied model context remains local
once the user deliberately sends it to an external model.

### Operating-system clipboard lifetime

After a successful Copy, the operating system or clipboard manager owns the
clipboard lifetime according to platform policy. The copied text can outlive the
Atrament browser document or backend session.

Session shutdown, bfcache cleanup, form clearing, or process exit removes
Atrament-owned in-memory copies but cannot be represented as guaranteed deletion
of an already exported system clipboard value.

First release does not automatically overwrite or clear the user's clipboard on
shutdown merely to simulate revocation. Such behavior could destroy unrelated
clipboard data or prevent the explicit external paste the user requested.

A later explicit Clear clipboard feature, if admitted, remains a presentation
operation and must state its platform limitations honestly.

### Clipboard write failure

Clipboard transport failure never changes accepted semantic state. The browser
distinguishes unavailable clipboard capability from a write attempt that failed
and exposes an accessible local status.

A failed Copy does not create a fake prompt receipt or mark a command context as
having reached an external model. The user can retry Copy or use another
explicit
text-transfer method without changing the backend request identity.

### Inbound paste

The external model response enters Atrament through the raw model-response text
surface. First release relies on the user's ordinary paste action; the browser
does not require background clipboard-read permission to ingest a response.

Pasted response text remains untrusted transport data. The browser does not
parse
semantic commands, allocate accepted IDs, validate scope, compute impact, or
apply notebook mutations from the pasted text.

An explicit backend validation/application step owns protocol parsing,
normalization, context binding, preconditions, provenance, writable scope,
capability checks, diagnostics, and atomic mutation.

### Paste does not imply Apply

Pasting command text into the response surface does not commit it. Interactive
command mode can validate and show the backend-owned semantic review projection
before an explicit acceptance action.

If the user selects only some returned commands, that selection follows the
selective rebatching contract. The browser does not delete lines or splice the
validated envelope and then apply the remainder.

### Inert text presentation

Prompt and response surfaces present command-like content as text.
Markup-looking
or script-looking content does not become HTML execution merely because it came
from source material or a model response.

The browser does not issue domain network requests, file operations, hardware
commands, or other application side effects because the displayed text contains
phrases that resemble those operations.

Backend validation remains necessary even when browser presentation is inert.
A response can be semantically malicious without containing executable browser
markup.

### No hidden clipboard persistence

Atrament does not maintain an application clipboard history, hidden response
archive, autosave journal, or browser storage copy merely to remember clipboard
round trips.

The active DOM and application state remain disposable. Explicitly exported
notebook or output files follow their owning persistence contracts rather than a
clipboard-history mechanism.

### MCP parity without clipboard

MCP automation projects the same backend command-context and semantic command
application model without routing structured data through the system clipboard.
Clipboard is therefore an optional human transport, not an intermediate required
for machine automation.

Equivalent clipboard-assisted and MCP command batches produce equivalent
application semantics after backend normalization and validation. Adapter-local
transport metadata and clipboard status are not notebook authority.

### Clipboard is not Export

Copying model request or response text is not the persistent Export application
capability. Export writes an admitted output through the explicit file boundary
and returns its own output identity and receipt.

Likewise, copying text does not turn the clipboard into an asset store, notebook
bundle, render manifest, or durable application database.

## Failure Modes

The contract fails if Copy mutates accepted state, if the browser constructs its
own semantic command context, or if text is parsed or executed in TypeScript as
an application command before backend validation.

Privacy claims fail if shutdown is described as revoking an already copied
system clipboard value, if credentials or hidden internal paths are included in
model context, or if clipboard round trips are silently archived by Atrament.

Inbound safety fails if Paste commits automatically, if model markup executes as
browser content, or if command-like prose causes network, file, export, or
hardware side effects without the owning backend application capability.

Parity fails if MCP requires a fake clipboard round trip or if
clipboard-assisted
input can reach semantic mutations that the shared application core would reject
through direct, CLI, or MCP paths.

## Verification

An exact-copy fixture presents a backend-generated Unicode command prompt,
performs one explicit Copy, and compares the browser value with the mocked
clipboard write byte-for-byte or code-unit-for-code-unit as appropriate to the
browser API. No semantic parser runs in TypeScript.

A hostile-text fixture includes script markup, a network request string, file
paths, hardware phrases, JSON-like commands, Unicode, and ordinary prose.
Browser presentation and clipboard transport preserve the text without executing
markup, issuing the described request, creating DOM children, or controlling
hardware.

A duplicate-copy fixture clicks Copy repeatedly for one unchanged prompt while a
write is active. Browser queueing does not manufacture several semantic requests
or mutate backend prompt identity.

A clipboard-failure fixture covers unavailable capability, synchronous failure,
asynchronous rejection, and malformed thenable behavior. Accepted notebook state
remains unchanged and local status remains actionable.

A paste fixture inserts a syntactically plausible semantic command envelope into
the raw response surface. No accepted mutation occurs until the backend command
boundary parses and validates it.

A shutdown fixture copies a known prompt, destroys the Atrament session, and
proves Atrament-owned DOM/session values are removed. The test does not assert
that the operating-system clipboard was revoked; documentation states that
external lifetime separately.

A parity fixture sends equivalent normalized command intent once through manual
clipboard transport and once through MCP structured context. Accepted revision
semantics, transaction provenance class, changed identities, impact, result
class, and typed diagnostics agree where the adapter distinction is not itself
part of the expected provenance.
